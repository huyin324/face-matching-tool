# face-matching-tool · 视频人脸匹配截取工具

> 给它一张人脸照片 + 一段视频，它自动告诉你「这个人出现在第几秒」，并把他每次出场的片段和最佳画面截取出来。
>
> GUI 桌面工具 · Python + PyQt6 · insightface + ONNXRuntime(CUDA) · 支持本地视频与 RTSP 实时流

## 一、它解决什么问题

监控排查、素材剪辑、活动录像归档最常见的需求是：**"把视频里所有出现某某人的地方找出来"**。
人工做法只能拖进度条一帧帧看，1 小时的素材要看一整天。

本工具把这件事全自动：

| 你提供 | 你得到 |
| --- | --- |
| 一张目标人脸照片 | 每次出场的时间点（精确到秒） |
| 一段视频 / 一路 RTSP 实时流 | 每次出场的视频片段 mp4（可省略） |
| （可选）连目标人脸都不用给 | 所有检测到人脸的高清抓图 |

典型场景：

- 监控录像中检索特定人员的所有出现时段
- 长视频（演唱会 / 会议 / 婚礼 / 课堂）中批量截取某人的镜头素材
- 无人值守 RTSP 摄像头实时流的自动抓拍与取证留档
- 从素材库中快速捞出「人脸最清晰的那一帧」用于建档

## 二、核心功能

### 1. 两种运行模式

| 模式 | 输入 | 触发条件 | 输出 |
| --- | --- | --- | --- |
| **人脸识别比对模式** | 目标人脸照片 + 视频 | 画面人脸与目标相似度 ≥ 阈值 | 红框标注截图（框上显示相似度，如 `98.50%`）+ 出场片段 |
| **人脸检测抓图模式** | 仅视频 | 检出人脸质量分 ≥ 阈值 | 所有人脸的绿框抓图（无需目标照片） |

### 2. 两种分析模式（V1.2 新增）

| 模式 | 推进方式 | 预览表现 | 适用 |
| --- | --- | --- | --- |
| **实时分析**（默认） | 按视频正常播放速度推进，边播放边比对 | 真实播放画面 | 需要边看边判断；RTSP 实时流 |
| **全速分析** | 不等待播放节奏，全算力解码 + 逐帧比对，尽快跑完全片 | 分析进度画面 + 实时「分析帧率」 | 只想要结果、追求最快出片 |

- 「全速分析」把检测队列改为**阻塞投递**，保证一帧不漏地送检（测下来分析帧数与传统实时模式完全一致，结果不会少）；
- 预览降频发送、队列满即丢，**UI 的绘制开销不会反向拖慢检测**；
- 仅本地视频可选；**RTSP 是实时流，无法脱离播放节奏，强制实时分析**（全速选项自动置灰）；
- 运行中可随时切换，无需停止重来。

> 实测（RTX 3060 Laptop / 1280x720@25fps / 6 秒素材 150 帧，多次运行区间）：
> 实时 22.6 ~ 22.7 fps、墙钟约 7.0s → 全速 **43.7 ~ 47.2 fps、墙钟 3.2 ~ 3.5s，约 2.0 ~ 2.2 倍**，两者截图产出完全相同。
> 上限来自 SCRFD 检测器本身（`app.get()` 约 22.5ms/帧 ≈ 44 fps），不是解码或显示。

### 3. 人脸优选（默认开启）

连续出场时逐帧截图会产生几百张几乎一样的图。开启优选后，在「优选时长」（默认 3 秒）窗口内**只保留人脸质量分最高的那一帧**，去重效果显著。

质量分综合了 6 个维度，不是单纯比大小：
`清晰度(Laplacian 方差) + 人脸尺寸 + 光照 + 对比度 + 正脸程度 + 居中程度`

低质量人脸（暗光 / 模糊 / 侧脸 / 像素过低 / 强光比）会被自动跳过，不参与比对，避免误判。

### 4. 出场片段截取

命中时刻向前 / 向后各保留 N 秒（默认各 10 秒，共 20 秒），自动拼接成完整出场片段。
本地视频走精确 seek 重编码；**RTSP 实时流走环形缓冲区**，实现「事后回捞」——即命中时刻之前的历史画面也能被保存下来。

### 5. 实时性与流畅性同时拉满

这是本项目重点打磨的部分。默认档位下（ RTX 3060 Laptop + 720p@25fps 实测）：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 检测帧率 | 3.7 ~ 5.4 fps | **23.0 fps**（≈ 逐帧） |
| 播放帧率 | 23 fps | **23.2 fps** |
| 目标框滞后 | 4.6+ 帧 | **平均 0.47 帧，最大 1 帧** |

即：**视频流畅播放与目标框紧贴人脸不再互斥**。详见 [第七章 · 性能优化实录](#七性能优化实录实测驱动非拍脑袋)。

### 6. 其他

- 多视频批量排队，逐个自动处理，中途可暂停 / 结束
- 支持 RTSP 实时流；播放恒定 1X（需要更快出结果请用「全速分析」）
- 自动检测 NVIDIA GPU：有则启用 CUDA，无则静默降级 CPU，无需手动切换
- 所有图片读写走 Pillow 的 UTF-8 封装，**中文路径 / 中文文件名不会报错**（本机 OpenCV 构建不支持中文路径）
- 一键启动：`launch.bat` 自动建虚拟环境、装依赖、补模型、启程序

## 五、参数详解

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 运行模式 | 比对模式 | 比对模式需目标人脸；检测模式无需目标人脸 |
| **分析模式** | 实时分析 | **实时**：按视频速度边播边比；**全速**：不按播放速度、全算力逐帧跑完（仅本地视频；RTSP 强制实时）。运行中可切换 |
| 分析帧率 | — | 界面实时显示，单位帧/秒。全速模式下可直观看到提速效果 |
| 相似度阈值 | 70% | 余弦相似度。调高更严格（漏检↑ 误检↓），调低更宽松。同一个人建议 60~75；光线差或角度偏可降到 55 |
| 人脸质量阈值 | 70 | 低于该分的人脸不参与比对/抓图。素材模糊时可降到 50~60 |
| 人脸优选 | 开启 | 在优选时长内只保留质量最高的一帧 |
| 人脸优选时长 | 3.0 秒 | 去重窗口。想要更多画面就调小或关闭优选 |
| 流畅性 ◀ ▶ 检测实时 | 75（逐帧） | 见下表。默认已可逐帧检测，偏左可降低显卡占用。**全速模式下该滑块禁用**（强制逐帧） |
| 关联视频 | 关闭 | 关闭时只出截图（快）；开启时额外产出命中前后的片段 mp4 |
| 关联视频前后时长 | 各 10 秒 | 命中时刻前后各保留的秒数 |

> V1.3 起不再提供「播放倍速」滑块：实时分析恒定按视频原始帧率播放（避免倍速跳帧导致漏检），
> 需要更快拿到结果请切换到「全速分析」——它是真正不丢帧的加速方式（实测约 2.0 倍）。

**平衡滑块档位**（`balance` → 每几帧检测一次）：

| 滑块值 | 检测间隔 | 适用 |
| --- | --- | --- |
| 85 ~ 100 | 每帧 + 紧跟踪模式（画面显示不领先检测） | 目标框必须严丝合缝，显卡有余量 |
| 67 ~ 84 | 每帧 | **默认 75**，流畅与实时兼得 |
| 34 ~ 66 | 每 2 帧 | 4K 素材 / 显卡吃紧 |
| 0 ~ 33 | 每 4 帧 | 纯 CPU 运行 |

## 七、性能优化实录（实测驱动，非拍脑袋）

初版的用户体验是「要么视频卡、要么框跟不上」。我们没有靠调参玄学，而是**先分阶段打点实测**，再对症下药。基线：`1280x720 @25fps`，每帧预算 40ms。

### 结论先行：检测是唯一真瓶颈

显示管线只占 3.08ms/帧，完全不是问题；而 `insightface app.get()` 单帧高达 **183~266ms**（3.7~5.4 fps），比视频帧率慢 5 倍。所以一切优化应围绕检测展开。

### 根因 1：`det_size` 未显式传入 —— 17~33 倍提速（最关键）

```python
# FaceAnalysis.prepare 的签名：prepare(ctx_id, det_thresh=0.5, det_size=None)
#                                                          ^^^^^^^^^ 默认是 None
```

`det_size=None` 会退化成动态尺寸列表 `[(128,128),(640,640)]`。而 buffalo_l 的 `det_10g.onnx` 输入是动态的 `[1,3,'?','?']`，**动态尺寸下 CUDA/cuDNN 无法缓存卷积算法，每帧都要重新搜索最优算法** → GPU 退化到 266ms/帧，比 CPU 还慢。

而早期的写法 `prepare(ctx_id, providers=...)` 会直接抛 `TypeError`，被 try/except 吞掉后回退到 `prepare(ctx_id=0)`，正好踩进这个坑，且**没有任何报错提示**。

```python
# 修复：显式固定检测尺寸
app.prepare(ctx_id=ctx_id, det_size=(640, 640))

# 附带：CUDA EP 选项
providers = [("CUDAExecutionProvider", {
    "device_id": 0,
    "cudnn_conv_algo_search": "HEURISTIC",     # 默认 EXHAUSTIVE 更慢
    "arena_extend_strategy": "kSameAsRequested",
}), "CPUExecutionProvider"]
```

**266ms → 13.8ms。**

### 根因 2：默认跑了全部 5 个模型

`allowed_modules=None` 时 buffalo_l 的 5 个模型会全部加载并逐个推理，其中 `genderage`、`landmark_3d_68` 本工具完全用不上，却要「每帧 × 每个人脸」各跑一次。

```python
# 按需裁剪
allowed_modules = ['detection', 'landmark_2d_106', 'recognition']  # 比对模式
allowed_modules = ['detection', 'landmark_2d_106']                 # 检测模式（不需要 embedding）
```

目标框滞后 1.35 → 0.69 帧，p95 6.9 → 2.35。

### 根因 3：片段截取与写盘阻塞检测线程

`extract_segment()` 会重新打开视频 + seek + 逐帧解码编码，一段 20 秒片段要几百毫秒到数秒，**期间检测完全停摆、目标框卡死**。截图写盘同理。

```python
class _IOWorker:
    """后台串行守护线程：检测线程只管投递任务，立即返回。"""
```

任务投递后即刻继续检测，写盘在后台串行完成。`wait_idle()` 用轮询 `unfinished_tasks` 而非 `queue.join()`，避免无超时死等。
验证：开启片段截取后仍是 23.12 fps / 滞后 0.48 帧，且正确产出 2 个 mp4 + 5 张 png。

### V1.2：全速分析模式的天花板在哪里

新增「全速分析」时，先问了一个问题：*不按播放节奏跑，到底能跑多快？* 于是把 27ms/帧逐段拆开实测：

| 环节 | 单帧耗时 | 结论 |
| --- | --- | --- |
| H.264 / MPEG-4 解码（1280x720） | 1.44 ~ 1.66 ms | 不是瓶颈 |
| `frame.copy()` | 0.52 ms | 可忽略 |
| 缩放到 896x504（`INTER_AREA`） | 1.93 ms | 可忽略（且每 2 帧才做一次） |
| **`eng.app.get()`** | **22.5 ms** | **唯一瓶颈，≈44 fps 上限** |

`app.get()` 这 22.5ms 里，即便画面**一张脸都没有**也要花掉——说明开销全在 SCRFD 检测器本体（640x640 前向 + CPU 侧预处理），与后续对齐 / 识别无关。

因此全速模式的做法不是"魔法提速"，而是**把播放节流彻底拿掉、让检测链满速跑**：

```python
# 实时：按帧率等待，检测再好也只能跑到视频帧率
time.sleep(frame_interval)

# 全速：不等；检测队列改为阻塞投递，队列满就等检测消费 —— 一帧不漏
if fs:
    if not self._put_blocking(self.det_q, item):
        break
```

实测结果与理论天花板吻合（46.3 fps vs 上限 44 fps，说明流水线已把检测器喂满）：

| 模式 | 实测帧率 | 墙钟（6 秒素材） | 分析帧数 | 截图 |
| --- | --- | --- | --- | --- |
| 实时分析 | 23.1 fps | 6.86 s | 150 帧（100%） | 2 张 |
| 全速分析 | **46.3 fps** | **3.26 s** | 150 帧（100%） | 2 张 |
| 全速（不产截图） | 46.4 fps | 3.26 s | 150 帧（100%） | 0 张 |

关键结论：

1. **提速约 2.0 倍**，且分析帧数与传统模式**完全一致**——快，但一帧都没少分析，结果不会漏。
2. **写盘不是瓶颈**：不产截图的对照组帧率几乎不变（46.4 vs 46.3），说明截图 IO 已被 `_IOWorker` 完全隔离。
3. 想再快只能动模型本身（减小 `det_size` 会牺牲小脸检出率），属于精度取舍，本项目默认不做。

### V1.3：把显示管线砍掉一半（省下的是 UI 线程，不是检测）

V1.2 拆帧时显示环节只有 1.93ms，看着不起眼，但它是**每帧都要在 UI 线程上付**的固定成本，在高帧率下会直接吃掉主线程余量、反过来拖慢投递。V1.3 对它做了三件事：

**① `QImage.Format_BGR888` 直通，省掉一次全图色彩转换**

旧写法为了迁就 `QImage.Format_RGB888`，每帧都要 `cv2.cvtColor(BGR→RGB)`；Qt6 提供了 BGR 原生格式，这次转换整个可以删掉。

```python
# V1.2：每帧多一次 1280x720 全图转换
rgb = cv2.cvtColor(frame_bgr, cv2.COLOR_BGR2RGB)
qimg = QImage(rgb.data, w, h, 3 * w, QImage.Format.Format_RGB888).copy()

# V1.3：BGR 直通，零转换
qimg = QImage(arr.data, w, h, 3 * w, QImage.Format.Format_BGR888)
```

**② 删掉多余的 `.copy()`**：`QPixmap.fromImage()` 本身就会把像素拷进 Qt 绘制后端，前面再 copy 一次纯属浪费（1280x720 约 2.7MB memcpy / 帧）。

**③ 一帧只拷一次，多个框原地画**：旧 `draw_box()` 每画一个框就 `frame.copy()` 一次整帧 —— 10 张脸就是 10 次全帧拷贝。新增 `draw_box_inplace()`，调用方拷一次、循环原地画。

三处合计的实测收益（`validate_v13.py` 的 C 部分基准，1280x720）：

| 写法 | 单帧耗时 | 像素一致性 |
| --- | --- | --- |
| V1.2（cvtColor + RGB888 + copy） | 1.712 ms | — |
| **V1.3（BGR888 直通 + 不 copy）** | **0.786 ms** | **逐字节完全一致** |

**快 1.2 倍（-54%），且画质零损失**（脚本会逐字节比对两条管线产出的像素，确认没有偏色）。

此外还固定了 `cv2.setNumThreads(4)`：OpenCV 默认可能拉起与核数相同的并行线程，与 onnxruntime 的推理线程争抢 CPU。A/B 实测两者吞吐一致（47.9 vs 47.6 fps），保留该设置是为了让行为在任何机器上都可预期，而不是为了提速。

V1.3 回归实测（同素材 150 帧，`RESULT: V13_OK`；两次独立运行的数字区间）：

| 模式 | 实测帧率 | 墙钟 | 分析帧数 | 截图 |
| --- | --- | --- | --- | --- |
| 实时分析 | 22.6 ~ 22.7 fps | 6.97 ~ 7.02 s | 150 帧（100%） | 2 张 |
| 全速分析 | **43.7 ~ 47.2 fps** | **3.21 ~ 3.47 s** | 150 帧（100%） | 2 张 |
| 全速（不产截图） | 44.8 ~ 47.9 fps | 3.16 ~ 3.38 s | 150 帧（100%） | 0 张 |

> 全速是实时的 **2.0 ~ 2.2 倍**（墙钟），与 V1.2 持平甚至略好——因为瓶颈自始至终都是 SCRFD 检测器（≈44 fps 天花板），显示管线的优化保住了 UI 余量，但动不了这个上限。

### 其他优化

| 项 | 做法 | 效果 |
| --- | --- | --- |
| 显示管线 | 工作线程预缩放到显示尺寸（`DISPLAY_MAX_W=1280`），UI 线程只做小帧→QPixmap；`_disp_scale` 换算框坐标 | 主线程开销与源分辨率解耦，4K 也不卡界面 |
| 全速预览降频 | 全速模式下每 3 帧才送一次预览（`disp_every=3`） | 约 15fps 预览完全够看，进一步压低 UI 侧开销 |
| 脏标记 | `_frame_dirty` 跳过无变化帧的重绘 | 减少无谓 repaint |
| RTSP 环形缓冲 | 宽 ≥960 的帧以 JPEG(q=92) 存储 | **788MB → 14MB（省 98.2%）**，画面平均误差仅 0.503 |
| 质量分计算 | `cv2.Laplacian` 由 `CV_64F` 改 `CV_32F` | 结果一致，耗时约减半 |
| 运动补偿追踪 | 速度 EMA 预测 + `max_miss=6` | 检测间隔内框位置平滑外推，不跳变 |

## 八、技术架构

### 线程模型

```
RunnerThread（编排）
├── PlaybackThread   读帧 → 环形缓冲 → 预缩放 → disp_q ──► UI 线程绘制
│                                       └─► det_q（实时：按 balance 抽样 / 全速：逐帧阻塞投递）
└── DetectThread     det_q → insightface 推理 → 追踪/匹配 → 结果回传
                                   │
                                   ├──► _IOWorker（后台串行：片段编码、PNG 写盘）
                                   └──► res_q('detfps') → 界面「分析帧率」
```

职责分离保证了**播放永不被检测阻塞**：检测再慢，画面依旧按帧率流畅播放，只是框更新频率下降。
全速模式只是把这套解耦流水线的**上游节流阀拆掉**，其余结构完全复用。

### 关键模块

| 模块 | 职责 |
| --- | --- |
| `detect_runtime()` | 探测 CUDA，组装 EP 与 providers，失败自动降级 CPU |
| `Engine` | insightface 封装：按模式裁剪模型、显式 `det_size`、质量分计算 |
| `PlaybackThread` | 取帧、预缩放、RTSP 环形缓冲、紧跟踪门控、实时/全速两种推进策略 |
| `DetectThread` | 推理、运动补偿追踪、命中判定、截图/片段调度、分析帧率统计 |
| `RingBuffer` | RTSP 历史帧缓冲（JPEG 压缩存储） |
| `_IOWorker` | 异步串行磁盘/编码任务队列 |
| `RunnerThread` | 模型加载 → 启动检测 → 逐个视频源播放 → 汇总 |

### 中文路径处理

本机 OpenCV 构建的 `imread`/`imwrite` 不支持中文路径。项目内统一封装：

```python
imread_utf8(path)   # Pillow 打开 → numpy（走 Python 文件 API，原生支持 Unicode）
imwrite_utf8(path)  # 自动建父目录 → Pillow 保存（失败再退回 cv2.imwrite）
```

`VideoCapture` / `VideoWriter` 传路径正常，仅图片读写需要封装。

## 十二、常见问题

**Q：双击 `launch.bat` 窗口一闪就没了？**
A：通常是 `.bat` 文件被改成 LF 换行导致 `goto` 失效，或 Python 未加入 PATH。项目中的 `.bat` 均已使用 CRLF；若仍闪退，在 cmd 中运行查看报错，或看 `launch.log` / `crash.log`。

**Q：明明有 NVIDIA 显卡却跑在 CPU 上？**
A：① `onnxruntime-gpu` 装成了 latest（需 CUDA 13，会静默回退）—— 必须锁 `1.22.0`；② 直接 `pip install insightface` 会把 CPU 版 onnxruntime 一起装上覆盖 GPU 版 —— 必须用 `--no-deps`。启动日志首行会标明实际后端。

**Q：总漏检 / 误检？**
A：漏检 → 降低相似度阈值（70 → 60）与质量阈值（70 → 55）；误检 → 反向调高。目标人脸照片尽量选正脸、清晰、光线均匀的。

**Q：截图太多？**
A：开启「人脸优选」并适当调大优选时长（3 → 5~10 秒）。

**Q：处理 4K 素材很卡？**
A：把平衡滑块调到 34~66（每 2 帧检测）。4K 的瓶颈在解码与缩放，与检测引擎无关。

**Q：什么时候该用「全速分析」？**
A：只想尽快拿到结果、不需要盯着画面看的时候。它不按播放速度推进，能把 1 小时的素材压到约 35 分钟跑完，结果与实时分析完全一致。

**Q：为什么「全速分析」不能用于 RTSP？**
A：RTSP 是实时流，画面按真实时间产生，没有"快进"这一说——脱离播放节奏也拿不到更多帧，因此强制走实时分析（选项会自动置灰）。

**Q：全速分析跑起来，预览画面像快进？**
A：正常现象。全速模式不按播放速度推进，预览显示的是"当前分析到哪一帧"，看「分析帧率」标签更能反映实际速度。

**Q：为什么全速只有 2 倍左右，不是 10 倍？**
A：瓶颈是 SCRFD 检测器本身，约 22.5ms/帧（≈44 fps 上限），实测 46 fps 说明流水线已经把检测器喂满了。再快只能牺牲检出率（减小 `det_size`），本项目默认不做这个取舍。

**Q：V1.3 为什么把「播放倍速」去掉了？**
A：倍速播放会**跳帧**，被跳过的帧不参与分析——它是"更快，但可能漏"。真正不丢帧的加速方式是「全速分析」（实测 2.0 倍、分析帧数与实时完全一致）。为避免这两个语义混淆，V1.3 直接移除了倍速滑块，实时分析恒定 1X。

**Q：日志栏跑到界面底部了，找不到？**
A：V1.3 的布局调整：日志改为**通栏置底**（高度约可显示 8 行），腾出的纵向空间全部给了左侧「目标人脸」栏——现在人脸预览会随窗口自适应放大，更好的核对目标长相。日志仍会滚动到最新一行，只是位置在界面最下方。

**Q：复选框为什么是个蓝底白勾的方块，不是系统的方框？**
A：V1.3 的复选框（`FlatCheckBox`）是自绘的：QSS 的 `::indicator` 要引用图片资源，而 QSS 里的相对路径是按**进程工作目录**解析的——双击 `launch.bat` 和从别处启动结果不一样，很脆。自绘没有资源依赖，勾选态固定画 √，线宽/圆角/配色都跟全局主题走。

**Q：从 V1.2 升级到 V1.3 需要注意什么？**
A：界面从 PyQt5 换到了 PyQt6。若你用的是自带 venv，`launch.bat` 会自动补齐 `pyqt6`；若是手动环境，执行 `pip install "pyqt6>=6.7.0"`（旧 PyQt5 可以留着不管，程序不再引用它）。
